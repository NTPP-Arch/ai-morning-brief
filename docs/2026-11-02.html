树形注意力 ZHA：报告在百万级上下文后拉开性能差距

发生了什么

《Subquadratic Attention with a Hierarchical Tree-Structured Indexer》提出 Zyphra Hierarchical Attention，简称 ZHA，目标是缓解长上下文注意力的计算增长。它不让每个查询平铺检查全部历史键，而是在 KV 缓存上建立递归压缩摘要组成的树。查询从树顶向下行走，最后只对选出的稀疏键执行注意力。

关键细节

论文强调，索引本身也要计入总成本，否则稀疏注意力可能只取得常数倍加速。作者称，通过随序列增长增加树深，路由加最终注意力的总成本随序列长度呈次线性增长，使整个注意力过程达到次二次、但仍超线性的规模。方法可通过覆盖数十亿 token 的短期 KL 蒸馏阶段应用于已有预训练模型。作者报告，长上下文检索，以及推理、数学和智能体编程评测的表现得到保持。树形结构测试覆盖最深 6 层；性能模型显示，它在超过 100 万上下文时显著优于所比较的方法。

⚠️ 边界

“数亿乃至数十亿 token 的有效窗口”在摘要中是潜力判断，不是已经交付的实测窗口。超过 100 万上下文后的优势也属于论文所用性能模型和比较条件，不能改写成任意硬件、任意任务上的现成吞吐结论。

Flide：决策查询最高比 vLLM、SGLang 快 9.5 倍

发生了什么

《Flide: Accelerating Decision Inference with Exact State Forking》为决策模型设计推理引擎，处理智能体一次请求中可能出现的多个查询分支。作者指出，面向生成任务的现有引擎用于这类负载时，可能反复计算相同前缀，或改变输出概率。Flide 试图同时处理共享计算和保持各分支原有结果这两个要求。

关键细节

它把请求的逻辑树与物理执行拆开，将多个分支放入一条扁平 token 流。ForkAttention 借助 GPU 上的索引，处理标准注意力层和循环式 Gated DeltaNet 层的依赖。论文称，在精确算术条件下，每个查询分支的计算与单独前向运行一致。GPU 常驻元数据还用于表达分支拓扑，使不同请求组合可复用一组预录制执行图。不断增长的智能体历史，可以从此前保存的检查点恢复；在公开混合模型和决策模型评测中，作者报告查询回答速度最高比 vLLM 和 SGLang 快 9.5 倍。

⚠️ 边界

“精确”对应精确算术下的分支等价保证，不应与实际浮点计算逐位相同混为一谈。9.5 倍是所测配置中的最高值；论文另以相对 float32 参考结果的总变差距离评价概率接近程度，并未声称所有查询都达到最高加速。

一句话点评

我认为 Flide 的工程意义在于：智能体要共享分支计算，不能以悄悄改变决策概率为代价。

来源：arxiv.org

多工具检索：工具找齐时成功 21/21，缺项时仅 2/39

发生了什么

《Completeness and Cost of Retrieval Structures for Multi-Tool Requests in LLM Agents》研究智能体需要调用多种工具时，检索器能否一次找齐。作者比较平面检索、查询拆解、层级导航、依赖图及训练过的集合级检索等结构。衡量重点不是某一工具是否排得靠前，而是任务所需的整套工具是否都落入前 k 个结果。

测试包括 345 条 AppWorld 查询，以及涉及 257 个 MCP 工具的 103 项 MCP-Bench 任务。对 7,961 条 ToolRet 查询的分析显示，前 10 项的完整率在单目标查询中为 .58 至 .67，在至少四目标查询中为 .08 至 .17。未在测试集上训练、每次查询最多调用一次 LLM 的所比较结构，在 AppWorld 的 k=16 条件下，没有一个完成超过 10% 的查询。用 75 至 90 条域内查询训练的集合级检索器，在 AppWorld 与 MCP-Bench 上分别达到 .33 和 .58，且检索时无需 LLM 调用。层级导航分别达到 .30 和 .40，但每次查询的 LLM 调用中位数为 31 至 38，耗时约五分钟。

DecisionRank：8B 排序器在指定测试中快 24.5 倍

发生了什么

《DecisionRank: On-Policy Distillation for Decision-Model Rerankers》把生成式模型的文档排序知识迁移给直接打分的决策模型。生成式教师输出文档 ID 的排序序列，学生则在首个 token 位置给文档打分，两者原本并不直接对应。论文提出在“条目空间”进行在线策略蒸馏，把学生的分数排序成序列，再交给教师反馈。

关键细节

训练同时结合离线排序监督，让教师的条件反馈直接指导学生分数。作者在 TREC DL、BEIR、BRIGHT 等一般与高推理要求的检索基准上评价该方法。论文报告，在四个基准中，条目空间在线策略蒸馏均优于所比较的训练目标。即使只有 1.7B 参数，DecisionRank 在 TREC DL19--23 上仍超过其 27B 生成式教师。8B 版本与生成式列表排序对应模型相比，在 TREC DL 上快 24.5 倍，在 BRIGHT 上快 16.7 倍；速度数字对应指定任务和对照方式。

⚠️ 边界

“学生超过教师”限定于论文列出的排序测试，不代表学生在教师的所有生成任务上都更强。8B 的速度对照对象是生成式列表排序模型，不能拿来与 Flide 的引擎加速数字直接比较。

一句话点评

我认为这项工作的方向很明确：当任务只需排序结果时，让模型直接评分，比让它先生成一份排序文本更合适。

来源：arxiv.org

KLM 披露负面结果：旧版打包曾漏掉 118/221 份含答案文本

发生了什么

《The Knowledge Layer Model (KLM): Evidence-Visible AI Output, Routing Diagnostics, and Negative Results》提出一种与实现方式无关的推理记录规范，让审核者看见答案所记录的证据、未知项和版本化判断。论文以 Nage AI OS 的 SEDIM 作为参考实现，也主动列出多项没有达到预期的内部结果。其论点是：答案看起来正确，并不足以替代可检查的依据。

关键细节

论文引用 KLM v0.3，对应仓库标签 v0.3.0，但说明各项内部实验并非端到端验证。历史路由基准报告在 15 类中答对 137/150；分子由四舍五入后的摘要恢复，历史样本归属未经核实。一次修正后的双来源测试中，原生模型权重路径配置成功数为 0/15。词面及限定范围诊断区分“沉默”与“矛盾”样例时，AUC 均为 0.008，低于预设最低值 0.65。旧版打包在选定的 221 个案例中漏掉 118 个含标准答案的文本；修复后，221/221 均保留了该文本。

⚠️ 边界

“保留含答案文本”测的是文本是否出现，不是答案是否正确，更不是模型是否因该证据作答。结果由作者内部报告，独立复现与完整公开审计包仍属后续工作；证据可见性也不自动证明安全性、因果依赖或合规性。

一句话点评

我认为把失败的诊断结果和修复前后的差别一起公布，比只展示一项漂亮准确率更有助于判断证据系统的实际能力。
